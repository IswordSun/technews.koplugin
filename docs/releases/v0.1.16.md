## ⚠️ 本版是修复版：请尽快从 v0.1.15 升级

### 修的是什么

**v0.1.15 在部分 Android 设备（如 Boox Nova3）上会导致「所有源都抓不到」。** 这是我的回归，先说清楚原因：

v0.1.15 为了省流量，让每个请求都声明 `Accept-Encoding: gzip`，但**没有先确认本设备能不能解压**。在加载不到 zlib、或解压实现不可靠的平台上，就变成「所有服务端都按 gzip 回、我们却解不开」→ 每一个源都失败。Kindle 与桌面不受影响（它们的库可用），所以问题只暴露在定制 Android 设备上。

### 怎么修的（三层保险，缺一不可）

| 层 | 行为 |
| --- | --- |
| **先探测** | 用 `pcall` 加载解压模块并实际探测；拿不到 zlib 就**不声明压缩**，服务端回明文（功能降级、可用性不受影响）。连模块加载本身都包在 `pcall` 里——它内部的 FFI 声明/库加载在某些平台上会抛错 |
| **运行期熔断** | 一旦真的解压失败，本设备**此后一律走明文**，并写入设置（重启后不再尝试） |
| **即时兜底** | 解压失败的那一次请求**立刻用明文重取**，不计入重试次数、不退避 |

另外给解压本身加了硬上限（轮数 + 输出字节），构造上不可能出现无限循环。

**结论：压缩从此只是一个"省流量"的优化，任何平台问题都不可能再让它拖垮抓取。**

## 顺带包含的改进

这些本来就在这次的工作里，一并给你：

### 图片阶段止损（重图源不再可能卡几小时）

爱范儿这类源一期有上百张图（前 20 条就有 335 张，原图平均 1.3MB）。此前一次网络失败会「800 宽失败 → 480 宽再试」，每次失败又是 4 次尝试 × 30 秒——**单张最坏 240 秒，150 张没有上限**。现在：

- **失败分类**：只有「这张图太大 / CDN 不接受缩放参数」才降宽度；网络层失败直接收手
- 图片下载改为 **1 次重试 / 10+25 秒超时**
- **按图床熔断**：同一图床连续 3 次失败，跳过它剩下的图（并在提示里计入略过数）
- 整期时间预算（300 秒）改为**逐张检查**，慢图下也真正生效

### 抓取过程看得见、取消得动

- 请求失败重试时，进度框会显示「**第 N 次重试（点击可取消）**」——以前只有一行「正在连接…」，看不出是在重试还是卡死
- **在重试之间点取消会立即生效**（不再需要等下一次请求）
- 图片进度显示已用时间：「下载图片 42/99（已 1 分 20 秒）」

## 升级方式

- **设置 → 检查更新**：应显示「更新到 v0.1.16」
- **如果设备当前正是 v0.1.15 且抓不到源**（更新检查也会打不开），请手动安装下方 ZIP：
  1. 解压 ZIP，得到 `zhifou.koplugin/` 目录
  2. 用 USB（MTP）连到电脑，进入 KOReader 的 `plugins/` 目录
  3. 旧的 `zhifou.koplugin` 先改名备份，再把新目录整个拷进去
  4. 重启 KOReader，「设置 → 关于」应显示 0.1.16

## 已知边界

- 知乎部分图片是「`.jpg` 的 URL 里装 PNG 字节」，其图床忽略转格式参数，只能按原样收录（判型与显示正常，仅体积压不下去）
- 更新包下载仍不支持断点续传（单个包约 130KB，影响有限）
- 「源连通性自检」只探测订阅源入口是否可达，不代表正文抽取一定正常
